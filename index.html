The Problem

Developers have no way to verify your server is safe

Right now, people decide whether to install an MCP server based on GitHub stars, README quality, and gut feel. There's no npm audit for MCP. No Sigstore. No Dependabot. If your server is legitimate, you have no way to prove it — and if someone clones your repo to distribute malware, you have no way to distinguish yourself from the clone.

This isn't hypothetical. Straiker's STAR Labs recently documented a supply chain attack that cloned a real MCP server, created fake GitHub accounts, and published the poisoned version to MCP registries. The original author had no recourse. Credence fixes that.

How It Works

You submit. We verify. Developers trust.

Credence gives your server a signed trust score — not based on stars or vibes, but on what's actually in the code.

01

We verify your identity

We confirm you're the repo owner, check account age and contributor history, detect forks, and flag provenance anomalies. If someone clones your server, the attestation points back to you — not them.

02

We scan the code

Static analysis, dependency CVE scanning, secrets detection, and MCP-specific checks — suspicious tool definitions, dynamic description loading, prompt injection patterns. We look at what the server actually does, not what the README says it does.

03

AI agents debate the findings

Five AI agents — skeptics, believers, and a neutral reviewer — argue about the scan results across multiple rounds. They're primed with real attack patterns from the wild. If a finding is ambiguous, the debate surfaces it instead of hiding it behind an arbitrary threshold.

04

You get a signed attestation

A cryptographically signed trust score pinned to your exact commit. Developers can verify it from the CLI, from their AI agent, or in CI — before they install. The attestation covers only the attested commit — new commits require a fresh scan.

The Debate Layer

A security team for every server

Traditional scanners produce a list of findings and a pass/fail. But security findings are rarely binary — a hardcoded string might be a leaked credential or a test fixture. A fork might be a supply chain attack or a legitimate contribution. Context matters, and thresholds are guesses.

Credence replaces the threshold with a debate. Five AI agents — each with a different security perspective — review the scan results and argue about what they mean. Skeptics look for attack patterns. Believers challenge false positives. A neutral reviewer synthesizes the positions into a confidence-scored verdict.

⚔

Adversarial Attacker + Supply Chain Analyst

The skeptics. Trained on real MCP attack patterns — SmartLoader TTPs, tool poisoning, coordinated fork networks. Their job is to find what the scanners missed and challenge anything that looks suspicious.

◉

Devil's Advocate + Pattern Matcher

The believers. They push back on overreaction — flagging when a "vulnerability" is actually standard practice, when a fork has legitimate provenance, when a finding is noise. Without them, every server gets flagged.

⚖

Compliance Reviewer

The neutral. Weighs both sides, checks for logical consistency, and produces the final verdict. The debate runs up to five rounds, terminating early when further argument stops producing new evidence.

The result is a verdict that captures uncertainty honestly instead of hiding it behind an arbitrary cutoff. Probabilistic issues require probabilistic solutions.

Consumption

Check trust before you install

Attestations are only useful if machines can read them. Credence provides three consumption interfaces — so the trust check happens automatically, not manually on a website.

⬡

MCP Server

Add Credence as an MCP server in Claude Desktop, Claude Code, or any MCP client. Your AI agent calls credence_check_server before connecting to unknown servers. Attestation data flows through the same protocol your agent already speaks.

>_

CLI

credence check owner/server from the terminal. Exit codes for CI integration: 0 = safe, 1 = not attested, 2 = flagged, 3 = rejected. Verify local source hashes against attestations before install.

⚙

Pre-Install Hook

credence guard wraps any install command with a trust check. If the server isn't attested or the score is below your threshold, the install doesn't run. Exit codes work in shell scripts, CI gates, and orchestration tools.

# Install
$ pip install git+https://github.com/pestafford/credence-registry.git#subdirectory=mcp-server

# Add to claude_desktop_config.json
{
  "mcpServers": {
    "credence": {
      "command": "python3",
      "args": ["-m", "credence_mcp.server"]
    }
  }
}

# Or from the terminal
$ credence check modelcontextprotocol/server-github
  Trust score:  91/100
  Verdict:      VERIFIED
  ✔ VERIFIED
When We Find Something

Responsible disclosure

Finding vulnerabilities is only useful if they get fixed. Credence gates publication on scan results and flags submissions for manual review when findings are serious.

▣

Submitter verification

The pipeline checks whether the submitter is the repo owner, a collaborator, or a contributor via GitHub API. Verified maintainers are labeled as such. Third-party submissions are scanned identically, but marked so reviewers know the context. Detailed scanner output is never published — only scores, verdicts, and provenance flags go into the public registry.

●

Clean or low-severity findings

Trust score reflects any minor findings in the dimension breakdowns. Attestation is signed and published to the registry automatically. Results posted to the GitHub issue.

●

Flagged or rejected

When the trust score is FLAGGED or REJECTED, the attestation is held from publication and the issue is labeled disclosure-pending. A maintainer reviews the detailed findings (stored as ephemeral artifacts with 90-day retention) and decides next steps — which may include contacting the repo owner privately before publishing.

↻

Re-attestation

After remediation, maintainers can submit a fresh scan at the new commit. The updated attestation replaces the previous one in the registry. Previous scan results remain in their scan-results/ directory.

Credence is a security tool, not a shaming tool. The goal is fewer vulnerable MCP servers in production, not more drama on security Twitter.

Roadmap

What's coming

Credence is in active development. The core pipeline — identity verification, multi-scanner analysis, adversarial deliberation, and signed attestations — is live today. Here's what we're building next.

▸

Tiered disclosure with remediation windows

Automated severity classification (low/medium/high) with configurable remediation windows. Medium findings get a 30-day private disclosure period before attestation is published. High findings trigger immediate review.

▸

Private maintainer notification

When actionable vulnerabilities are found, contact the repo owner directly — before anything is published. Include specific remediation guidance: dependency upgrades, secret rotation steps, tool description rewrites.

▸

Pre-install source verification

Extend credence guard to clone, hash, and verify local source against the attestation before install. Catch tampering between attestation and installation.

▸

Lockfile drift detection

Compare lockfile hashes across successive attestations for the same server. Flag when dependencies change between scans — even if the code hasn't.

▸

Registry and platform integration

Notify MCP registry operators (MCP Market, Glama, Smithery) when high-severity findings are confirmed. Report manufactured identity operations to the hosting platform.

▸

Attestation history

Consumer-facing view of a server's full attestation timeline. See when issues were found, when they were fixed, and how trust scores evolved across versions.
